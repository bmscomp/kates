Open source · Apache Kafka · Kubernetes

Break your Kafka cluster before production does.

You find out how a Kafka cluster handles a broker failure on the day a broker fails, unless you have already tried it. Kates puts load on Apache Kafka, injects faults into its brokers, measures what they cost in throughput, P99 latency, recovery time and lost records, and audits broker security configuration.

Why Kates

Most teams test Kafka resilience with two terminals and a hunch.

A perf-test script in one window, kubectl delete pod in another, and a Grafana board someone eyeballs. Kates turns those checks into tests you can repeat, run in a pipeline and grade against targets you set.

Performance

How many records per second can the cluster sustain before latency degrades? Where is the capacity limit?

Resilience

What happens to in-flight messages when a broker dies? Does the cluster recover from a network partition within the SLA?

Data integrity

Is there any data loss under cascading failures? Are ordering and exactly-once guarantees kept under stress?

What it does

One toolkit, from load generation to the audit report.

Performance tests

Eight workload types: LOAD, STRESS, SPIKE, ENDURANCE, VOLUME, CAPACITY, ROUND_TRIP and INTEGRITY. Real Kafka producers and consumers on virtual threads, or hand the workload to Trogdor.

Reports: throughput, P50/P95/P99, error rate. Exports: CSV, JUnit XML, Markdown, HTML, latency heatmaps.

Fault injection

Thirteen disruption types, from broker pod kills and network partitions to CPU, memory and I/O stress, DNS errors, disk fill and node drain, executed through LitmusChaos or a direct Kubernetes provider.

Blast-radius guard, dry run, automatic rollback.

Resilience runs & disruption plans

Pair one load test with one fault and get the before/after change and the recovery time. Or run multi-step disruption plans with ISR and consumer-lag tracking and an A–F SLA grade.

Built-in playbooks for the failures you fear most.

Security audit

Grade broker configuration A–F. Map the checks to CIS, SOC 2 and PCI DSS, save a baseline and report drift from it on the next run.

kates security audit · kates security gate

CI gates

Exit non-zero below a minimum performance or security grade, or when a scenario file violates its SLA. Webhooks notify your pipeline when a test finishes.

JUnit XML out of the box. History kept in PostgreSQL for trends.

A multi-zone lab on one machine

A three-node Kind cluster whose nodes sit in separate zones, each with its own StorageClass and broker pool, with rack awareness on. Rehearse a full zone failure on a laptop.

Twelve Grafana dashboards, Prometheus alert rules and OTLP traces included.

Quick start

From an empty laptop to a graded load test in five commands.

You need Docker, Kind, kubectl and Helm, and about 16 GB of RAM. Everything else, Strimzi, Kafka, Prometheus, Grafana, LitmusChaos and the Kates API, is installed by kates deploy.

  1. Install the CLI with Homebrew, or download a single binary from the latest release.
  2. Create the lab: a three-zone Kind cluster named panda.
  3. Deploy the stack with a wizard, or --dry-run to see the plan first.
  4. Open the ports: the CLI context is configured with the API URL and key.
  5. Run a test and read the graded report.
Full quick start Deployment guide
Terminal
# 1. The CLI (macOS or Linux)
brew install bmscomp/tap/kates
git clone https://github.com/bmscomp/kates && cd kates

# 2. A three-zone Kind cluster named panda
make cluster
make kates-native

# 3. The stack: Strimzi, Kafka, monitoring, chaos, Kates API
kates deploy

# 4. Port-forwards and a ready CLI context
kates ports

# 5. A first load test, then a CI gate
kates test create --type LOAD --records 100000 --wait
kates gate --min-grade C --records 100000

Architecture

Three parts that fit how you already run Kafka.

Performance tests work against any Kafka cluster the Kates API can reach. Fault injection targets Strimzi-managed brokers. Every run is stored, so the numbers from last month are there to compare with today's.

CI gates

Make resilience a build step, not a quarterly exercise.

Describe a workload and its SLA in a scenario file. Kates runs it, injects the fault, checks every gate and exits non-zero when one fails. The same file runs on a laptop and in the pipeline, and every run lands in PostgreSQL so a regression shows up as a trend, not a surprise.

  • kates gate --min-grade B for a one-line performance gate
  • kates security gate for the broker configuration grade
  • JUnit XML for your CI dashboard, webhooks for everything else
  • A GitHub Action, bmscomp/kates, ready to drop into a workflow

Try the failure before it tries you.
