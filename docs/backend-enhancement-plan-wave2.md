# Backend Enhancement Plan — Wave 2 (Engine Correctness & Runtime Resilience)

Audit date: 2026-07-23. Scope: the Quarkus backend under `kates/` (~190 main + 55 test Java files, Quarkus 3.20.6 LTS, Java 21). All file:line claims verified against source.

Wave 1 (`docs/backend-enhancement-plan.md`, complete) hardened the **perimeter**: secrets, SSRF, bean validation, persisted state, HA-safe scheduling, Testcontainers, CVE gates, the Quarkus 3.20 LTS bump, native-image readiness. Wave 2 goes **inward**, into the parts wave 1 didn't reach: the async test-lifecycle engine, the correctness of the numbers the tool reports, the chaos rollback path, and the runtime signals Kubernetes acts on. The backend is well-tended (0 TODO/FIXME, spotless-enforced, migrations that document the bug each fixed) — but a benchmark tool is only as trustworthy as its measurements and its ability to reach a terminal state, and both have real defects today.

The finding that reframes everything: **this is a Kafka benchmark tool whose core produce-latency metric is measured at the wrong point, and whose runs do not reliably transition to DONE.** Those two are P0 because they undermine the product's primary purpose, not merely its polish.

## P0 — Correctness of the core function

**P0-1. Producer latency is measured at enqueue, not at ack.** `engine/NativeKafkaBackend.java:207-220`: `sendStart` is captured, `producer.send(...)` returns after appending to the accumulator buffer, and `latencyMs = (nanoTime - sendStart)` is recorded *there* — then the callback (lines 208-215) only records ack/fail to `AckTracker`, never the latency. So `histogram.recordLatency` captures **buffer-append time**, not the broker round-trip. With batching/linger this reports latencies that are wildly, misleadingly low — the headline number of a performance tool is wrong. **Fix:** capture `sendStart` per sequence and compute `nanoTime - sendStart` *inside* the send callback (the callback already exists and already keys on the record); record into the histogram there. Small change, highest leverage in the codebase.

**P0-2. Runs don't reach DONE without a client polling.** `engine/TestOrchestrator.refreshStatus` (`:311`) is the *only* place a RUNNING run transitions to terminal, records final metrics, and clears handles — and it's called only from `api/TestResource.java:199` (client GET) and the resilience path. A benchmark whose workers finish successfully stays RUNNING in the DB until someone polls; if nobody does, `engine/TestTimeoutReaper.java:32` marks the **successful** run FAILED at 30 min. **Fix:** add a `@Scheduled` reconciler (every few seconds) that calls `refreshStatus` for every active handle — or have workers push terminal state via a completion callback. Either makes completion self-driving and stops false FAILEDs.

**P0-3. The reaper marks runs FAILED but never stops the workers.** `engine/TestTimeoutReaper.java:47-59` updates the DB row but does not call `backend.stop()`, so producer/consumer virtual threads keep hammering Kafka after the run is "failed" — a resource leak that also corrupts any concurrent run's numbers. **Fix:** call `orchestrator.stopTest(runId)` (which stops the handle) from the reaper, not just a DB update.

**P0-4. `SCALE_DOWN` chaos rollback restores the wrong replica count.** `disruption/DisruptionSafetyGuard.java:244-270`: `restoreReplicaCount` derives the "desired" size from `ss.getStatus().getReplicas()` — the *already-scaled-down* current status — because the pre-disruption count is never snapshotted. A failed or timed-out scale-down step therefore leaves the Strimzi StatefulSet **permanently shrunk**; rollback can't restore the original size. **Fix:** capture `spec.replicas` into the step state *before* scaling and restore from that snapshot.

## P1 — Runtime resilience & observability truth

**P1-1. Health probes are wired to the wrong signals — they cause the failures they should prevent.** `api/KatesLivenessCheck.java:28-52` returns DOWN on heap pressure, so a large benchmark that legitimately tightens heap gets the pod **killed and restarted mid-test** (restart storm). `api/KatesReadinessCheck.java:26` calls `clusterHealthService.isReachable()` with a 10s Kafka timeout, so a transient Kafka blip pulls the *entire* API — including Kafka-independent endpoints — out of the Service. **Fix:** liveness keeps only a deadlock/liveness signal (never heap); readiness uses a cached/periodic, non-fatal Kafka indicator rather than a synchronous 10s probe on every kubelet check.

**P1-2. Prometheus cardinality leak + dead metrics in `BenchmarkMetrics`.** `engine/BenchmarkMetrics.java`: meters are tagged with the unbounded `run_id`, and `endRun` (lines 41-44) removes only the map entry, never the registered meters — there is **no `registry.remove` anywhere in the codebase**, so every run permanently adds time series (a slow Prometheus OOM). Worse, `recordLatency`/`recordThroughput`/`recordError`/`recordSlaViolation` have **zero callers**, so the per-run gauges that *are* registered always read 0. **Fix:** drop `run_id` as a meter tag (use it as an exemplar/log field instead) or `registry.remove` on `endRun`; delete the dead recording methods or wire them into the engine. Pairs with P1-3.

**P1-3. Per-run `LatencyHistogram`s all register the same global-scoped gauges.** `engine/LatencyHistogram.java:17-27` registers `kates.latency.p50…` tagged `id="global"`, and every `WorkerState` builds `new LatencyHistogram()` (`NativeKafkaBackend.java:350`). Micrometer dedups on name+tags, so only the *first* run's histogram is ever exported (behind a weak ref that later goes stale) — every subsequent run's percentiles are invisible. **Fix:** thread the task/run id into the `LatencyHistogram` constructor so each run's gauges are distinct (and bounded — see P1-2's cardinality note; scope to task, not raw run_id, or remove on completion).

**P1-4. Disruptions execute synchronously over HTTP with no orphan recovery.** `disruption/DisruptionResource.java:72` calls `orchestrator.execute(plan)` inline and returns the finished report — a plan is minutes long (`steadyState + chaosDuration + observationWindow + recoveryTimeout≤300s` per step × N), so it holds a worker thread and the client connection past every LB/read timeout, and is inconsistent with the async 202 pattern tests already use. Separately, `disruption/DisruptionOrchestrator.java:68` runs the whole plan in-process and rolls back only on in-process exception; if the pod is killed mid-plan the injected NetworkPolicy/scale-down **persists with nothing to clean it up** (tests have `recoverOrphans`; disruptions have no equivalent). **Fix:** run disruptions on a virtual thread, return `202` + a report id, expose status via GET (mirror `TestResource.createTest`); persist per-step state and reconcile `managed-by=kates` faults on startup.

**P1-5. The concurrency limiter guards submission, not execution.** `engine/TestOrchestrator.java:118-146` acquires a `maxConcurrentTests` permit, runs `executeAsync` on a vthread, and releases in `finally` — but `executeAsync` only *submits* (each `backend.submit` starts its own long-lived worker vthread and returns in ms, lines 166-189), so the permit is released while the workload still runs. Net: the concurrency cap is ineffective and `activeTestCount()` (surfaced to the liveness probe, line 430) reads ~0 during real load. **Fix:** hold the permit for the run's lifetime (release on terminal transition in the P0-2 reconciler), or derive the active count from non-terminal handles.

## P2 — Performance ceilings in the measurement path

**P2-1. `LatencyHistogram` serializes every sample behind a write lock.** `engine/LatencyHistogram.java:13-38`: a single HdrHistogram guarded by a `ReentrantReadWriteLock`, `recordLatency` taking the **write** lock per record. On a multi-producer STRESS/CAPACITY run (millions rec/s) the measurement path is itself the throughput ceiling — the tool can't measure loads it induces. **Fix:** `org.HdrHistogram.Recorder` / `ConcurrentHistogram` (lock-free recording, snapshot on the read side).

**P2-2. Rate limiter busy-spins a carrier thread.** `engine/NativeKafkaBackend.java:188-195`: throughput-capped producers loop on `Thread.onSpinWait()` until the next send window, burning a whole carrier thread per capped producer. **Fix:** `LockSupport.parkNanos(nextSendNanos - now)`.

**P2-3. `AckTracker` allocates per-record entries in two skip-list maps → OOM on large runs.** `engine/AckTracker.java:40-41,63-66`: `states` + `sendTimestamps` hold one boxed-`Long` entry per sequence; INTEGRITY/ENDURANCE at 10M records ≈ 20M entries (hundreds of MB). **Fix:** primitive-keyed structures — a fixed `long[]`/`AtomicLongArray` sized to `maxMessages`, or roaring bitmaps for the ack set.

**P2-4. CDC test runs blocking Kafka I/O + `Thread.sleep` on the common ForkJoinPool.** `engine/CdcIntegrationService.java:94` (`CompletableFuture.supplyAsync` with no executor) plus `Thread.sleep(2000)` polls at 407/480/673 starve `commonPool`. **Fix:** pass the existing bounded `KatesExecutor` (wave 1 introduced it for exactly this).

_Quick wins to batch here:_ static `ObjectMapper` singleton in `service/TestRunRepository.java:35` (currently `new` per save); escape/​structure the SASL JAAS string in `config/KafkaSecurityConfig.java:107-121` (unescaped concat breaks on a password containing `"`/`\`); narrow `security/ApiKeyAuthFilter.java:26` from the blanket `/q/` public prefix to `/q/health` + `/q/metrics`.

## P3 — Data layer & durability

**P3-1. Outbox: write-amplification and delete-before-ack.** `service/TestRunRepository.save:22-45` writes an outbox row on **every** save — including each status poll and each reaper pass — so the outbox floods with duplicate `test.lifecycle` events instead of one per real state change. Then `service/OutboxPoller.java:40-48` calls `eventEmitter.send(...)` (async, returns a `CompletionStage`) and **immediately** `em.remove(event)` in the same transaction, before the broker acks — an async send failure after commit silently loses the event, defeating the outbox's at-least-once guarantee. **Fix:** enqueue only on an actual status change; delete the row in the send-completion callback (or set `published_at`), not synchronously. Add `idx_outbox_created_at` (the poller does `ORDER BY created_at ... FOR UPDATE SKIP LOCKED` every 2s with no index — `V13`), and a retention job for `processed_events` (`V14`, grows forever).

**P3-2. `merge()` + `orphanRemoval` rebuilds all child rows on every save.** `persistence/EntityMapper.toEntity:28-48` builds fresh `TestResultEntity` children with null IDs each call; with `cascade=ALL, orphanRemoval=true` (`persistence/TestRunEntity.java:63`) each save deletes and re-inserts the entire results collection — O(results) delete+insert on *every poll* of a multi-task run. **Fix:** load-and-mutate the managed entity (an unused `updateEntity` already exists) or diff by task id.

**P3-3. No optimistic locking.** No `@Version` on `TestRunEntity`, yet `refreshStatus`, `stopTest`, `TestTimeoutReaper`, and `recoverOrphans` all read-modify-write the same run with last-write-wins `merge` — the reaper can clobber a concurrent legitimate completion (compounds P0-2/P0-3). **Fix:** add `@Version`; add an `OptimisticLockException` mapper (the `GlobalExceptionMapper` has none).

## P4 — Testing the risk

The bugs above cluster in exactly the classes with the least coverage: 50 unit tests but only **2** integration tests, and `NativeKafkaBackend` (the actual engine), end-to-end `TestOrchestrator`, `DisruptionOrchestrator`, `OutboxPoller`, and `SecurityService` (1747 LOC) have **zero** tests. Wave 1 added the Testcontainers harness (`PersistenceIT`, `KafkaAdminIT`) — wave 2 should extend it to the engine and the async lifecycle:

- Testcontainers IT for the produce→ack→histogram path asserting **latency is the round-trip** (guards P0-1 forever) and the run reaches DONE via the reconciler (P0-2).
- Outbox IT covering the failure-before-ack case (P3-1) and the "one event per state change" invariant.
- Disruption IT for `SCALE_DOWN` rollback restoring the original replica count (P0-4) and startup orphan reconciliation (P1-4).
- Ratchet the jacoco floor (currently 10%, `pom.xml:353`) **per-package**, prioritizing `engine`/`disruption`/`service`.

## Sequencing

- **Week 1 — P0 (correctness):** P0-1 (latency-at-ack) and P0-3 (reaper stops workers) are one-file changes; P0-2 (reconciler) and P0-4 (scale-down snapshot) are small and self-contained. Land with the P4 engine IT that pins each. This is the wave's whole justification — do it first.
- **Week 2 — P1 (runtime truth):** health-probe decoupling (P1-1) and the metrics fixes (P1-2/P1-3) as one observability pass; disruption async + orphan recovery (P1-4) and the concurrency-permit fix (P1-5) as one lifecycle pass.
- **Week 3 — P2/P3:** the measurement-path perf ceilings (Recorder, parkNanos, AckTracker) and the data-layer durability fixes (outbox ack-ordering, index, `@Version`), each behind an IT.

No architectural rewrites required — every P0/P1 item is a localized change to a specific method, and the god-class decomposition (`SecurityService`, `ClusterTopologyService`) is explicitly out of scope for this wave (tracked in wave 1's P3). The theme is narrow and high-value: **make the numbers true and the lifecycle self-healing.**
